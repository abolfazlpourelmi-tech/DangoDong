# تست مهاجرت‌های دیتابیس

مهاجرت‌ها روی Supabase میزبان اجرا می‌شوند و قوانین دسترسی را همان‌جا اعمال
می‌کنند — یعنی اشتباه در آن‌ها یا داده را خراب می‌کند یا اجازه‌ای می‌دهد که
نباید. این پوشه اجازه می‌دهد قبل از دست‌زدن به production همه‌چیز روی یک
PostgreSQL موقت اجرا و بررسی شود.

## اجرا

```bash
supabase/tests/run.sh
```

به یک PostgreSQL محلی نیاز دارد (`initdb`، `pg_ctl`، `psql`):

```bash
brew install postgresql@16        # macOS
sudo apt install postgresql       # Debian/Ubuntu
```

اسکریپت یک نمونه‌ی موقت می‌سازد، آن را در پایان پاک می‌کند، و **هیچ‌وقت به
دیتابیس میزبان وصل نمی‌شود**. اگر قانونی نقض شود با کد خروج غیرصفر و نام همان
قانون شکست می‌خورد.

## اجزا

| فایل | نقش |
|---|---|
| `schema-stub.sql` | جای‌گزین اسکیمای میزبان؛ فقط جدول‌ها و ستون‌هایی که اپ می‌خواند و می‌نویسد |
| `migrations.test.sql` | قوانین دسترسی به‌صورت ادعاهای اجرایی |
| `run.sh` | نمونه‌ی موقت را بالا می‌آورد، مهاجرت‌ها را اجرا می‌کند و تست‌ها را می‌سنجد |

`run.sh` هر فایل داخل `../migrations` را به‌ترتیب نام اجرا می‌کند، بعد **یک بار
دیگر** اجرا می‌کند تا مطمئن شود مهاجرت‌ها idempotent هستند و دوباره اجرا کردنشان
چیزی را خراب نمی‌کند.

`auth.uid()` در stub از روی یک setting خوانده می‌شود، پس تست‌ها با
`set request.jwt.claim.sub = '<uuid>'` هویت عوض می‌کنند و می‌توانند رفتار
کاربران مختلف را بسنجند.

## افزودن مهاجرت جدید

۱. فایل مهاجرت را در `../migrations` بگذار (پیشوند تاریخ، تا ترتیب حفظ شود).
۲. اگر ستون یا جدول تازه‌ای لازم دارد که هنوز در `schema-stub.sql` نیست، آنجا
   هم اضافه‌اش کن — وگرنه تست‌ها به دلیل اشتباهی شکست می‌خورند.
۳. برای هر قانون دسترسی که مهاجرت اعمال می‌کند، در `migrations.test.sql` یک
   ادعا بنویس: `pg_temp.ok(...)` برای چیزی که باید درست باشد و
   `pg_temp.denies(...)` برای فراخوانی‌ای که باید رد شود.
۴. `run.sh` را اجرا کن.

نکته: ادعایی که نمی‌تواند شکست بخورد ارزشی ندارد. بعد از نوشتن هر تست، قانون
مربوطه را عمداً خراب کن و مطمئن شو تست واقعاً قرمز می‌شود.
